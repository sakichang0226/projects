# 課題: 注文履歴画面のN+1問題とテーブル設計

## 背景

注文履歴画面の実装において、現在のテーブル設計（orders → sub_orders の2段階Query）ではN+1問題が発生する。

### 現状の設計
- ordersテーブル: PK=user_id, SK=order_id
- sub_ordersテーブル: PK=order_id, SK=sub_order_id

### 問題
ordersから10件取得後、各order_idごとにsub_ordersをQueryする必要があり、合計11回のDynamoDBアクセスが発生する。

---

## 検討した解決策

### 案1: ordersにキー情報List埋め込み + sub_ordersのSK変更

- ordersにList型（L）で `sub_order_keys` を追加
- sub_ordersのSKを `seq`（連番）に変更、`sub_order_id`は通常属性に降格
- 取得: Query orders → BatchGetItem(PK=order_id, SK=seq)

| Pros | Cons |
|------|------|
| BatchGetItemで一括取得（2回のアクセス） | sub_ordersのSK構造変更が必要（既存設計への影響大） |
| sub_ordersに正規化データが1箇所で管理される | ordersにList型でキー情報を持つため、注文確定時にordersも更新が必要 |
| 店舗単位のsub_order_idを属性として維持可能 | List型の中身（seq）の採番管理が必要 |
| | BatchGetItem上限100件の考慮が必要（最大200件） |

### 案2: ordersに明細データを非正規化埋め込み

- ordersにList型（L）で `sub_orders` を追加（商品名・価格等の表示用データを全て埋め込み）
- sub_ordersテーブルは変更なし（管理画面専用として維持）
- 取得: Query ordersのみ（1回で完結）

| Pros | Cons |
|------|------|
| 1回のQueryで注文履歴画面の全データ取得完了 | ordersとsub_ordersの二重書き込み（データ二重管理） |
| sub_ordersテーブルの構造変更不要 | 整合性リスク（片方だけ更新されるケース） |
| BatchGetItem上限を気にする必要なし | ordersのアイテムサイズが肥大化（DynamoDB上限400KB） |
| 最もアクセス回数が少ない | 配送ステータス更新時にordersの埋め込みデータも更新が必要 |
| | 店舗単位のsub_order_idをどこに持つか別途検討が必要 |

### 案3: 商品単位を維持 + 管理画面はアプリでグルーピング（採用候補）

- ordersにNS型で `sub_order_ids` を追加（商品単位の連番Set）
- sub_ordersは現設計維持（PK=order_id, SK=sub_order_id、1レコード=1商品）
- 管理画面の店舗単位グルーピングはアプリケーション側で `order_id` によりgroup by
- 取得: Query orders → BatchGetItem(PK=order_id, SK=sub_order_id)

| Pros | Cons |
|------|------|
| テーブル設計の変更が最小限（ordersにNS追加のみ） | 店舗単位の受注IDが存在しない（将来必要になったら追加対応） |
| sub_ordersテーブル構造がシンプル（1レコード=1商品） | 管理画面でorder_idによるグルーピングロジックが必要 |
| 注文確定時の書き込みが素直（二重管理なし） | BatchGetItem上限100件の考慮が必要（最大200件） |
| DynamoDB Local検証済みの設計がそのまま使える | |
| 将来の拡張（shop_order_id追加等）が容易 | |

---

## 総合比較

| 観点 | 案1 | 案2 | 案3 |
|------|-----|-----|-----|
| テーブル変更の影響 | 大 | 中 | 小 |
| 実装の複雑さ | 中 | 中 | 低 |
| DynamoDBアクセス回数 | 2回 | 1回 | 2回 |
| データ整合性リスク | 低 | 高 | 低 |
| 管理画面対応 | 容易 | 容易 | アプリ側対応 |
| ポートフォリオ適性 | △ | △ | ◎ |

---

## DynamoDB Local検証結果

案3の方式でDynamoDB Localにて動作確認済み。

1. **Query**: orders（PK=user_id）→ 注文一覧 + `sub_order_ids`（NS型）取得
2. **BatchGetItem**: 取得したorder_id + sub_order_idの全組み合わせで一括取得 → 成功（UnprocessedKeys空）

---

## 補足事項

### BatchGetItem上限について
- カート上限: 20商品種類/注文
- 最大ケース: 10注文 × 20明細 = 200件 → BatchGetItem上限100件を超える可能性あり
- 対応: 100件ずつ分割してBatchGetItemを呼ぶ（実装上の軽微な考慮）

### sub_order_idの粒度変更
- 元々は「店舗単位」で想定していたが、案3では「商品単位」に変更
- 店舗単位の受注IDが将来必要になった場合は、sub_ordersに `shop_order_id` 属性を後から追加で対応可能

### 複合SK案（不採用）
- ordersのSKを `order_id#sub_order_id` にして1テーブルに統合する案も検討
- ページネーション要件（注文単位で10件、lastOrderIdでカーソル指定）との相性が悪いため不採用

## 議論経緯

### 案1推進（バックエンドエンジニアA）
- 正規化維持 + N+1解消。データの信頼できるソースがsub_orders 1箇所に集約される
- 配送ステータス更新時もsub_ordersだけ更新すればよい
- 反論への応答: 本番稼働前の今なら SK構造変更は許容できる

### 案2推進（フロントエンドエンジニアB）
- 1回のQueryで完結し、レイテンシが最も低い。ユーザー体感に直結する
- 反論への応答: TransactWriteItemsで同時書き込みすれば整合性は担保可能

### 案3推進（インフラ/設計エンジニアC）
- ポートフォリオという前提では変更量最小が最優先
- 案1はSK構造変更のマイグレーションコスト、案2は二重管理の運用バグリスクがある
- 管理画面のグルーピングはorder_idでgroup byするだけ（数行のロジック）
- 店舗単位の受注IDは将来必要になった時にsub_ordersへ属性追加で対応可能（YAGNI原則）
- BatchGetItem上限200件問題は現実的にほぼ発生せず、超えても100件ずつ分割するだけ

---

## 決定事項

**案3を採用。**

### 採用理由
1. テーブル設計の変更が最小限（ordersにNS型`sub_order_ids`追加のみ）
2. DynamoDB Localで動作検証済み
3. データ整合性リスクが低い（二重管理なし）
4. ポートフォリオ規模に対して過剰設計を避けられる
5. 将来の拡張（店舗単位受注ID等）にもスキーマレスの特性で対応可能

### 採用後のテーブル設計

#### ordersテーブル
| 属性名 | 型 | Key | 説明 |
|--------|-----|-----|------|
| user_id | N | PK | ユーザーID（JWTから取得） |
| order_id | N | SK | 注文ID |
| created_at | N | - | 注文日時 UnixTimestamp(ms) |
| sub_order_ids | NS | - | 受注明細IDのSet（商品単位） |

#### sub_ordersテーブル
| 属性名 | 型 | Key | 説明 |
|--------|-----|-----|------|
| order_id | N | PK | 注文ID |
| sub_order_id | N | SK | 受注明細ID（商品単位の連番） |
| user_id | N | - | ユーザーID |
| shop_id | N | GSI1-PK | 店舗ID |
| product_id | N | - | 商品ID |
| product_name | S | - | 商品名（注文時点のスナップショット） |
| price | N | - | 注文時単価 |
| order_num | N | - | 注文数 |
| created_at | N | GSI1-SK | 受注日時 UnixTimestamp(ms) |
| delivery_status | S | - | 配送ステータス（PR:処理中 / ED:配送済み） |

### 注文履歴取得フロー
1. Query orders（PK=user_id, 降順, Limit=10）→ 注文一覧 + sub_order_ids取得
2. BatchGetItem sub_orders（PK=order_id, SK=sub_order_id）→ 全明細一括取得

### 残課題
- BatchGetItemが100件を超える場合の分割処理実装
- 管理画面でのorder_idによるグルーピングロジック実装
- 店舗単位受注IDが必要になった場合のsub_orders属性追加（将来対応）
